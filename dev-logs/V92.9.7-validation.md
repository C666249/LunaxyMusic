## Product/performance review

- FluidToolDock uses one ~500ms reversible master progress. Child windows overlap strongly with ~65–75ms start separation, so action 2 begins before action 1 lands. Reversal derives from the same progress; no queued child Animator.
- Saved playlists >=120 songs take the recycling `ListView + BaseAdapter` path. UI work scales with the visible viewport, while tapping a row still installs the complete playlist as the playback queue.
- Long-playlist viewport is stored as first visible position + top offset and restored across refresh / tab context restore.
- Playback position snapshots no longer trigger full large-playlist adapter rebinding; only current-song identity or artwork accent changes do.
- Long-playlist delete persistence executes on background IO and applies the final result on main without rebuilding the page.
- Playlist-local search is 110ms debounced, filtered on a dedicated single-thread executor, generation-cancellable inside the scan loop, and displayed through a recycling ListView. Existing results stay readable until the newest filter completes.
- Global search freezes the visible head after first paint; later providers exact-variant merge / stable-append. A coalesced merge captures its frozen head when it actually launches, preventing an early-empty-snapshot race from re-ranking visible rows.
- Search summary content signature observes visible identities rather than total background result count, reducing remove/rebuild flashes while providers continue filling in.
- LibraryStore caches decoded playlist JSON only in-process; persisted format/key are unchanged.
